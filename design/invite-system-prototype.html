四 · 数据与状态

邀请关系表 invite_relations

列类型说明
invite_idBIGINT PK AUTO_INCREMENT邀请关系主键
inviter_idBIGINT NOT NULL邀请人。不建外键，邀请人注销后此 id 成为悬空 id，行仍保留
invitee_idBIGINT NOT NULL · 唯一索引被邀请人。唯一索引保证一个新用户只算在一个人名下，一次写定不可改绑
register_timeDATETIME NOT NULL等于被邀请人 users.created_at，同一服务端时刻
statusVARCHAR(16) · CHECK仅描述被邀请人：REGISTERED / INVALID（被邀请人已注销）
created_at / updated_atDATETIME NOT NULL审计列，沿用项目既有约定

配套在 users 表新增 invite_code VARCHAR(8) NULL + 唯一索引 uk_users_invite_code。 邀请码 8 位，字母表 ABCDEFGHJKLMNPQRSTUVWXYZ23456789（剔除易混的 I/O/0/1），注册时生成，存量用户首次进邀请页时惰性补齐，之后终身不变。

注销语义（本次调整）

被邀请人注销→行保留 · status 置 INVALID · 不计入已邀请人数 · 昵称以空值返回
邀请人注销→行全部保留 · status 一律不变 · 邀请码释放可被后续新用户重新占用

因此 invite_relations 不含任何指向 users(id) 的外键，是「只追加 + 状态更新」的历史表， 注销只影响能不能登录，不影响这条链路还在不在。邀请人注销后其名下的行不再能被任何已认证接口读出（该账号已无法登录，接口数据范围硬性限定为令牌用户本人），仅供后台统计。 代价是失去了外键兜底，所以插入前需在应用层校验 inviter_id 存在。

绑定结果与未绑定原因

登录/注册响应统一返回一个绑定结果标识，未绑定时附带唯一原因，多条件同时成立时按固定优先级取首个：

NO_CODE› NOT_NEW_USER› CODE_NOT_FOUND› SELF_INVITE› ALREADY_BOUND
  • 绑定时机唯一：只在新账号被创建的那一刻建立。老用户带码登录不绑定，所以互邀刷量和改绑问题从根上不存在。
  • 邀请码问题绝不阻断注册：缺失、格式错、查不到、自邀、已绑定，一律照常签发令牌，只在响应里说明没绑上。唯一会回滚整个登录事务的情况是「唯一约束冲突以外的数据库故障」。
  • 唯一约束冲突走保存点：捕获后仅回滚到保存点、继续提交，以 ALREADY_BOUND 完成登录，新用户不受影响。

微信生态的两个限制

  • 「邀请链接」不是 HTTP 链接：微信外的普通链接无法直达小程序，所以邀请链接是小程序页面路径 /pages/invitelanding/invitelanding?code=XXXXXXXX，用于分享卡片的 path 与小程序码的 page。不引入 URL Link / H5 中转页。
  • 二维码是微信小程序码：服务端调 wxacode.getUnlimited（scene 放邀请码），返回 base64 PNG。项目当前没有对象存储，所以不落盘，只做服务端内存缓存（7 天、至多 1000 项）。同时按 user_id 限流：24 小时内未命中缓存至多 20 次。

本期不做

不发奖励、不做多级分销、不做邀请链路追溯。status 取值与表结构留了扩展空间，奖励规则等后续 spec 再加。
